# 项目问题汇总（Issue Register）

> 版本：v1.0（2026-09-21 建立）· 状态：**持续更新**，每次提交前同步。
> 定位：**全项目唯一的「问题/风险/待决」清单**。跨 `design.md` / `docs/*.md` / `AGENTS.md` 汇总，并按「严重度 + 状态」排序，供评审与开发排期使用。
> **文档边界**：本文件只负责「问题 / 风险 / 待决的汇总、定级与状态跟踪」。其余事实按 [`docs/api.md`](./api.md) §0「文档事实单一来源」引用，**不复述可漂移的数值**。
>
> **与其它文档的分工**（避免出现第二个清单）：

| 文档 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| **本文件** | **问题的汇总、去重、定级、跟踪**；每条给「现象/影响/建议动作/出处」 | 不定义设计方案（按「出处」跳转） |
| `AGENTS.md`「困难与问题记录」 | **历史发生过的**问题与解决过程的原始记录（只追加不篡改） | 不做定级与跨文档汇总 |
| `docs/data-interfaces.md` §12 | 导入契约内部的**开放问题**（Q1-Q16） | 不覆盖其它领域的问题 |
| `docs/module-M6-map.md` §12 | 地图模块内部的**开放问题**（Q-1…Q-6） | 同上 |
| `docs/module-M2-base-data.md` §11 | 基础数据模块内部的**待决项**（Q1-Q6） | 同上 |
| `docs/build-plan.md` §7 | **构建阶段**的技术风险与缓解 | 不含功能与契约问题 |
| `AGENTS.md`「设计决策记录」 | 已作出的**决策**（编号与**状态以该表的「状态」列为准**） | 不记录未决问题（见 ISS-007 / ISS-017） |

**维护规则**（三选一，每条问题必须处于其中一种状态）：

1. **新增**：发现即入表，编号顺延（`ISS-0xx`），必须写「现象 + 影响 + 建议动作 + 出处」四段。
2. **状态流转**：`待办` → 处理中 → `已解决`（保留条目，标注解决日期与提交号）。
3. **不删条目**：即使已解决或被驳回，也保留原文并把状态改掉——已排除的问题（如 ISS-028）对后来者最有价值。

#### ISS-009 · `EventBus` 未按会话权限过滤，领域事件广播给全部窗口

| 项 | 值 |
| --- | --- |
| 严重度 | `P1`（阻断 / 优先） |
| 状态 | `已解决（2026-09-21）` |
| 类型 | 安全 |
| 领域 | 后端 / 安全 |

**现象**：`desktop/src/services/event-bus.ts` 的 `emit()` 对 `this.targets`（所有已 attach 的
`webContents`）**无条件群发** `udm:event`，不判断接收方会话的角色与权限点。

**影响**：与 D-08「权限校验双轨制」冲突——接口层做了服务端强制校验，
但事件通道绕过了它。只要有第二个窗口/会话连接，就能收到它无权查看的对象事件
（如 `alert.*` 给 monitor、`task.*` 给无 `task:read` 的角色）。
单窗口演示形态下不可见，接多角色后是真实的越权面。

**建议动作**：`EventBus` 持有「target → session」映射（`attach()` 时绑定会话），
`emit()` 前按事件类型所需权限点过滤。`docs/architecture.md` 已记为缺口（「M6/M8 落地时补」），
建议提前到 M8 之前，因为它属于安全边界而非功能特性。
**出处**：`desktop/src/services/event-bus.ts` · `docs/architecture.md` 第 10 章与 §8.2 缺口表

**解决（2026-09-21）**：`EventBus` 改为**按会话权限过滤**后再推送（deny-by-default）。

- 新增 `EVENT_PERMISSIONS`：事件类型 → 所需权限点（`task.changed`→`task:read`、`vehicle.changed`/`execution.progress`→`monitor:read`、
  `alert.created`/`alert.updated`→`alert:read`、`settings.changed`→`settings:read`）。未登记的类型（如刷新信号 `map.updated`）视为公开。
- `attach(target, token?)` 绑定会话；新增 `bindSession(target, token)` 供登录/登出升降权；
  未登录窗口**收不到**任何登记过权限的事件。
- `main.ts` 的 `udm:invoke` 在 `/api/auth/login` 成功与 `/api/auth/logout` 后同步窗口身份。
- `EventBus` 构造器第二参数改为**必填** `sessions` —— 省略它会让所有事件被静默丢弃，让编译期就报错好过运行时排查。
- **事件日志照写不误**（服务端真相不受过滤影响），只过滤**推送**。
- 新增 `desktop/src/services/event-bus.test.ts`（8 条用例：未登录 / monitor / dispatcher / 登出降权 / 公开事件 / 落库 / 销毁 / 权限映射完备性）。

#### ISS-034 · `npm run dev` / `dev:electron` 在干净检出上因未构建 `shared` 而无法启动

| 项 | 值 |
| --- | --- |
| 严重度 | `P1`（阻断 / 优先） |
| 状态 | `已解决（2026-09-21）` |
| 类型 | 可运行性 |
| 领域 | 工程化 |

**现象**：在**干净检出**（`node_modules` 已装、但 `shared/dist` 与 `desktop/dist` 不存在）上执行
`npm run dev` 或 `npm run dev:electron`，Vite 能启动并打印 ready，但页面**拿不到入口模块**；
浏览器控制台/终端报：

```text
[vite] Pre-transform error: Failed to resolve entry for package "@udm/shared".
The package may have incorrect main/module/exports specified in its package.json.
```

Electron 侧同样起不来：`npm run start --workspace desktop` 执行 `electron dist/main.js`，
而 `desktop/dist` 不存在。

**影响**：**这是新使用者/新机器的第一步**（README「本地运行」第一条就是 `npm run dev`），
失败即劝退；且失败形态具误导性 —— Vite 显示 `ready in 113 ms`、`/` 返回 200
（SPA 兜底），看起来「启动了」，实际白屏。排查者容易误判为 React Flow 或渲染层问题。

**原因**：workspaces 的**源码**依赖被当成了**已构建产物**依赖。
`shared/package.json` 的 `main`/`exports` 指向 `./dist/index.js`，而 `dist/` 被 `.gitignore` 排除；
`renderer` 与 `desktop` 在**运行时**（非仅类型）从 `@udm/shared` 导入：

| 位置 | 运行时导入（非 `import type`） |
| --- | --- |
| `renderer/src/components/AppLayout.tsx` | `hasPermission` |
| `renderer/src/api/mock.ts` | `ERROR_CODES` |
| `renderer/src/api/mock-data.ts` | `SEED_IDS` |
| `desktop/src/main.ts` · `ipc/*` · `services/*` · `db/seed.ts` 等 | `APP_NAME` / `SETTINGS_SCHEMA` / `DomainError` / `SEED_ACCOUNTS` … |

`test` / `typecheck` / `db:*` 四个脚本都**已经**带 `npm run build:shared`，
唯独 `dev` 与 `dev:electron` 没有 —— 不是设计选择，是漏加。

**建议动作**：给 `dev` / `dev:electron` 补上与其它脚本一致的预构建步骤。

**解决（2026-09-21）**：`package.json` 两处脚本前置构建，**改动仅 2 行**：

- `dev`：`npm run build:shared && npm run dev --workspace renderer`
- `dev:electron`：`npm run build:shared && npm run build:desktop && concurrently …`
  （桌面端还要 `desktop/dist/main.js`，同样不能假定已存在）

未选用的替代方案：给 `shared` 加 `dev` 走源码（需改 `exports` 指向 `src`，会让 Electron 主进程加载 `.ts`）；
或在 `prepare` 钩子里构建（`npm install` 之后自动跑，但会拖慢安装且对「只跑 renderer」的人不必要）。
当前方案与既有 `test`/`typecheck`/`db:*` 的写法完全一致，成本最低、认知负担最小。

**验证**：删除 `shared/dist` 与 `desktop/dist` 后复跑两条命令，均一次通过 —— 见
`AGENTS.md` 2026-09-21「修复干净检出无法启动」工作日志条目的实测记录。

**出处**：`package.json` · `shared/package.json`（`main`/`exports` 指向 `dist`） · `README.md`「本地运行」

#### ISS-066 · 契约写 `POST /api/auth/login`，实现按缺省的 `GET` 注册（照文档调用会 404）

| 项 | 值 |
| --- | --- |
| 严重度 | `P2`（重要） |
| 状态 | `已解决（2026-09-26）` |
| 类型 | 契约一致性 |
| 领域 | 契约 / 主进程 / 渲染层 |

**现象（实测）**：M5 走查时照 `docs/api.md` §3.1.1 写了一段 E2E 脚本，用 `POST /api/auth/login`
登录 —— 返回 `API.ROUTE_NOT_FOUND`（`detail: { path: '/api/auth/login', method: 'POST' }`）。
改用 `GET` 才通。同一时刻，**界面登录完全正常**，全部 750 个用例也是绿的。

**影响**：分两类使用者，受损的只有一类：

- **界面 / 现有调用点**：它们全部走 `apiClient.invoke('/api/auth/login', …)` **不传方法**，
  而 `client.ts` 的默认值是 `GET` —— 于是「实现按 GET 注册」与「调用点按 GET 发」互相吻合，
  整条链路自洽，界面毫无异常（`/api/auth/logout` 同理）；
- **照文档调用的第三方**：HTTP 形态的客户端、外部集成、**照着契约写的 E2E 脚本**一律拿到 404。

这正是 `ISS-002` / `ISS-055` 的同一族：两端各自「自洽」，差别只在有没有人**照文档**调用；
而「文档与实现不一致」的两种修法（改文档 or 改代码）后果完全不同 —— 契约里写 POST 是有理由的
（登录创建会话、退出销毁会话，都不是幂等读），因此修的是**实现**。

**根因**：`Route.method` 是**可省字段**，省略时 `router.ts` 一律按 `GET` 注册 —— 那是为兼容
早期只有读接口的调用点而做的**有意设计**（文件头写明）。两者单独看都对，缺的是
**「契约写了方法、实现漏写」这件事没有任何断言**：路由 ↔ 契约的断言（`ISS-052`）只比对**路径**，
把 `:id` 归一成 `{id}` 后 `includes` 一下即可，**方法从未进入比对范围**；
渲染层三层适配器的一致性用例也全部用不传方法的调用点，因此三种形态一起错、一起绿。

**解决（2026-09-26）**：

1. `desktop/src/ipc/api.ts` 给 `/api/auth/login` 与 `/api/auth/logout` 显式写上 `method: 'POST'`，
   并在注释里记下这条教训（光看这一行代码看不出问题）；

#### ISS-069 · 同一辆车在一批里出现两条计划时，apply 整批回滚并报一句与事实无关的错

| 项 | 值 |
| --- | --- |
| 严重度 | `P2`（重要） |
| 状态 | `已解决（2026-09-27）` |
| 类型 | 实现缺陷 |
| 领域 | 服务层 / 实现 |

**现象**：在调度中心「全选 → 预览 → 应用派发」，界面弹出二次确认框（里面写着「派 2 单」），
点「确认应用派发」后红条提示 **「车辆状态不允许该操作」**，库里一条计划都没落。
同样的操作在只有一条任务时完全正常。

**根因**：内核**允许一辆车在一批里出现多条计划** —— 每条计划维护半开占用区间
（`docs/module-M4-dispatch.md` §6），后一个任务只要自然落在前一个区间之外就同样可行。
最直观的一例是「车已在 B 仓时同时接 B→A 与 A→B 两单」：两段区间首尾相接，`runDispatch`
输出**两条都挂在 CAR-01 上**的计划。

但落库时「预留」写成了 `idle → reserved` 的**单向跃迁**（`reserveVehicleIfIdle` 的
`WHERE status = 'idle'`）：处理第二条计划时 `rowCount` 为 0，被当作「车被别人抢走了」，
抛 `VEHICLE.STATE_CONFLICT`，单事务整体回滚。于是使用者看到的是「车辆状态不允许该操作」，
**而实际情况是两单都能派** —— 提示与事实无关，且没有任何线索指向「同一辆车出现两次」。

**影响**：这是「先预览后生效」这条主链路上的**静默失效**：预览说能派、应用永远失败，
且失败原因指向错误的方向（会让人去查车辆状态，而车没有问题）。单任务场景、全部单测、
以及只需一次预留的走查路径**都是绿的**，所以它在实现完成后才在端到端走查里显形。

**建议动作**：把「本批次已由我们预留」与「车被别人抢走」区分开 —— 前者跳过预留、后者才失败。

**解决（2026-09-27）**：`apply` 维护 `reservedInBatch: Set<vehicleId>`，每辆车在**首次**使用时
才走一次 `idle → reserved` 条件更新；同时新增一条守卫 —— 同一辆车的两次占用若**时间重叠**
（存档被改动或来自旧版实现），抛 `DISPATCH.PLAN_EXPIRED` 要求重新预览，而不是把两条
互相矛盾的占用写进库。Mock 侧（`renderer/src/api/mock-dispatch.ts`）用同一判据对齐。
回归用例：`dispatch.service.test.ts`「同一车串行拉两单」+`mock-dispatch.test.ts` 的同名用例
（两侧都断言「一次派成两条、车辆只 `reserved` 一次」），并**反向验证**过：把 `reservedInBatch`
短路改回旧行为，两条用例立刻转红。

**出处**：`desktop/src/domain/dispatch/dispatch.service.ts` · `desktop/src/db/repositories/dispatch-plan.repo.ts` · `renderer/src/api/mock-dispatch.ts`（`docs/api.md` §3.4.3 已补该形态与「回收语义」）

#### ISS-070 · 重算回收一条计划时无条件把车辆置 `idle`，而该车可能还挂着另一条生效计划

| 项 | 值 |
| --- | --- |
| 严重度 | `P2`（重要） |
| 状态 | `已解决（2026-09-27）` |
| 类型 | 实现缺陷 |
| 领域 | 服务层 / 实现 |

**现象**：与 `ISS-069` 同源、但症状相反且更隐蔽。同一辆车上有两条生效计划时，
对其中**一条**执行「回收并重算」：任务确实回到 `pending`、原计划也确实作废，
**但车辆同时被置成 `idle`** —— 而它身上还挂着另一条未完成的计划。

**根因**：`recompute` 的回收循环是「取出该任务名下的 `applied` 计划 → 逐条释放车辆」，
判据只有「这条计划属于这个任务」，没有问过**这辆车还有没有别的生效计划**。
在「一车一批只接一单」的假设下这个写法是对的 —— 而该假设恰恰是 `ISS-069` 已经否掉的那个。

**影响**：库里出现「车辆状态 = `idle`，却挂着 `applied` 计划且任务为 `assigned`」的矛盾组合。
下一次调度会把这辆**实际上仍被占用**的车当作空闲派出去，两条计划的占用区间真重叠；
而事后查库时，两条计划各自都是自洽的、车辆状态也合法，
**没有任何单一字段能指出是哪一步错了**。这是本项目最不愿留下的那类数据形态
（与 D-25 拒绝冗余列、D-07 保留引用完整性同一条理由）。

**建议动作**：回收的语义应是「释放**这一单**的占用」；只有当该车不再被任何其它生效计划占用时，才把状态改回 `idle`。

**解决（2026-09-27）**：新增 `hasOtherActivePlanForVehicle(db, vehicleId, excludeTaskIds)`，
`recompute` 逐条回收前先判一次；Mock 侧用等价的 `store.plans.some(...)` 对齐。
回归用例：`dispatch.service.test.ts`「重算回收一单时，同一辆车上仍挂着的另一单不受影响」
（断言「回收一单后车辆仍 `reserved`，两单都回收后才回 `idle`」），同样反向验证过会转红。

**出处**：`desktop/src/db/repositories/dispatch-plan.repo.ts` · `desktop/src/domain/dispatch/dispatch.service.ts` · `renderer/src/api/mock-dispatch.ts`

#### ISS-063 · `slow_edge` 警告在「全网速度一致」时对每条路线都触发

| 项 | 值 |
| --- | --- |
| 严重度 | `P3`（一般） |
| 状态 | `已解决（2026-09-26）` |
| 类型 | 实现缺陷 |
| 领域 | 算法内核 / 渲染层 |

**现象（实测）**：M5 内核首次跑通时，一条**理想路线**（起终点直连、全程同速）也返回了一条警告：
`途经边 … 限速 1.5 m/s，为全网最低速段`。根因是「最低速段」的判据写成了
`edge.speedMps <= graph.minSpeedMps` —— 当全网速度一致时，**每一条边都满足它**。

**影响**：这不是「多显示一行字」。`warnings` 是界面用来回答「这条路线为什么慢 / 为什么不理想」的字段，
而当每条路线都带同一条提示时，它就退化成噪音 —— 使用者会学会**忽略整个警告区**，
于是真正有意义的绕行提示也一起被忽略。这是 D-48 那条原则的另一个形态：
**说不出口的名字不该来自拼接，无意义的信号会淹没有意义的信号**。

**根因**：判据只写了「是不是最低速」，漏了前提「**速度确实有差异**」。
两处都很自然：写条件时想的是「找出最慢的那一段」，而「全网只有一种速度」时这个问题**没有答案** ——
它不该被回答，而不是被回答成「每一条都是」。

**解决（2026-09-26）**：`buildWarnings` 先算 `speedVaries = graph.maxSpeedMps > graph.minSpeedMps`，
仅在其为真时才产生 `slow_edge`；`RouteGraph` 因此保留 `maxSpeedMps` / `minSpeedMps` 两个字段
（空图为 0，故「没边」不会被误判成「速度一致」）。测试补一条「每条路线不再无条件带警告」的用例。
**解决出处**：`shared/src/route-search.ts`

#### ISS-064 · 用例写死了任意一条等长路线，实际两条走法都可能被选中

| 项 | 值 |
| --- | --- |
| 严重度 | `P3`（一般） |
| 状态 | `已解决（2026-09-26）` |
| 类型 | 测试缺陷 |
| 领域 | 算法内核 / 测试 |

**现象（实测）**：`compare` 的一致性用例断言「A* 与 Dijkstra 的 `nodeIds` 逐项相等」，
在 4×3 网格上**失败**：A* 给出 `[…n02, n06, n07, n11…]`，Dijkstra 给出 `[…n02, n06, n08, n12…]` ——
两条**里程与耗时完全相同**的路线。另有两条内核用例把某条等长走法写成期望值（如
`['n1','n4','n5','n6','n3']`），同样只对实现当时的 tie-break 顺序成立。

**影响**：这类用例比「测不到」更糟：它把**实现细节**（谁先被展开）当成契约。
后续任何改动（换 tie-break、换堆的稳定性）都会让它变红，而变红的原因是**测试写错了**，
不是代码坏了 —— 维护者于是学会「这类红灯改期望值就行」，而真正的退化会在这层豁免里溜过去。

**根因**：把「最短路」这个概念当成了「唯一的那条路」。网格图（每段等长、无权重差异）里
最短**路径集合**通常有多个元素，选哪一个由 tie-break 决定 —— 契约（`docs/api.md` §3.5.2）
明确定义「一致」是**里程与耗时**相同，不是节点序列相同。写测试时照「路的形状」断言，
而没照契约里的判据。

**解决（2026-09-26）**：改为断言**性质**而不是形状 —— `distanceM` / `durationS` 相等、
`edgeIds` 长度相等、`consistent === true`；内核里那两条也改成「含某节点 + 不含某直达边 + 里程更大」
这类不随 tie-break 变化的性质。并在 `route.service.test.ts` 的对应断言旁写明**为什么不能断言序列**
（这条注释比断言本身更重要：它是下一次有人想「顺手加个序列相等」时的拦截点）。
**解决出处**：`desktop/src/domain/route/route.service.test.ts` · `shared/src/route-search.test.ts`

#### ISS-065 · 测试用 `n6` 当孤岛，但那张网格图里 `n6` 是连通的

| 项 | 值 |
| --- | --- |
| 严重度 | `P3`（一般） |
| 状态 | `已解决（2026-09-26）` |
| 类型 | 测试缺陷 |
| 领域 | 算法内核 / 测试 |

**现象（实测）**：为了覆盖 `ROUTE.NOT_FOUND_PATH`，用例把 `n6` 从图里摘掉当成孤岛；
但测试用的 `gridNodes()` 生成的是 3×3 网格，`n6` 在里面是**中心节点**，连通性最好。

#### ISS-067 · 半开区间相交谓词漏判空区间

| 项 | 值 |
| --- | --- |
| 严重度 | `P3`（一般） |
| 状态 | `已解决（2026-09-26）` |
| 类型 | 实现缺陷 |
| 领域 | 算法内核 |

**现象**：`intervalsOverlap(a,b,c,d)` 的实现是 `a < d && c < b`。当 `a === b`（零长度区间）
且该时刻落在 `[c,d)` 内部时，两个条件同时成立，函数返回 `true` —— 一个**不含任何时刻**的区间
被判成与别人冲突。

**影响**：按当前调用方（`t3 = t2 + executeTimeS`，恒大于 `t2`）**不会真实发生**，
所以它不是线上缺陷；但它是「半开区间」这个模型里最容易写错的一处，
下一个改动（例如允许零时长任务、或把等待单独建模成零长度槽）会直接踩上来，
而表现是「明明没占用却派不出去」。

**根因**：半开区间的相交公式 `a < d && c < b` 是**针对非空区间**的判据；
空区间需要单独排除。公式本身写对了，**前提没写进代码**。

**解决（2026-09-26）**：谓词前置 `aFrom < aTo && bFrom < bTo`，并补一条用例
「零长度区间不与他人冲突」把这条语义钉住。
**解决出处**：`shared/src/dispatch-evaluate.ts` · 用例 `shared/src/dispatch-occupancy.test.ts`

#### ISS-071 · 调度日志的「重算」行套用「派 x/y · 拒 n」模板，读起来像任务丢了

| 项 | 值 |
| --- | --- |
| 严重度 | `P3`（一般） |
| 状态 | `已解决（2026-09-27）` |
| 类型 | 界面缺陷 |
| 领域 | 渲染层 |

**现象**：走查时日志面板里出现一行「重算 · 派 0/1 · 拒 0 · 代价 0.0 · 0ms」——
同一时刻屏幕上方的推荐语写着「指派 1/1」。两处数字互相矛盾，第一个反应是「这一单去哪了」。

**根因**：日志行的 `summary` 由 `logRowOf` 统一拼成「派 x/y · 拒 n · 代价 c · tms」，
而**重算记录的 `summary` 语义不是派发**：重算的动作是「作废旧计划 + 回收车辆 + 任务回 `pending`」，
新建议在同 `requestId` 的那份**预览**里、且**尚未应用**（§10.4 有意不自动应用）。
服务端为这条记录写的 `summary` 恒为「0 派 / 0 拒」，套模板就成了「派 0/1 · 拒 0」——
一句话里既没派也没拒，等于告诉使用者「这单凭空消失了」。

**影响**：数字本身没算错（`docs/module-M4-dispatch.md` §14 的记录与实现一致），
错的是**用同一个模板讲了两件不同的事**。它不报错、不影响数据，只会让人对日志产生一次错误怀疑 ——
而日志面板存在的全部意义就是「可复核」。

**建议动作**：重算行单独给一句话（说清它产出的是「回收了几条计划、新建议待确认」），不套派发模板。

**解决（2026-09-27）**：`logRowOf` 对 `action === 'recompute'` 返回
「回收 N 条计划 · 新建议待确认」，其余动作仍是四件事一起说（保留原有信息量）。
新增用例断言重算行**不含**「派 0/1」，并同时断言其它动作仍走原模板（避免为了修一行把别的路径改掉）。
实测两形态（Electron / 浏览器 Mock）日志行均为「回收 1 条计划 · 新建议待确认」。

**出处**：`renderer/src/dispatch/model.ts` · `renderer/src/dispatch/model.test.ts`

#### ISS-072 · CDP 走查里动态 `import` 会拿到第二个模块实例，脚本报成功而界面是空的

| 项 | 值 |
| --- | --- |
| 严重度 | `P3`（一般） |
| 状态 | `已排除`（不是产品缺陷；已写入走查脚本纪律） |
| 类型 | 走查方法 |
| 领域 | 工具 / 用法 |

**现象**：浏览器 Mock 形态的走查脚本里，用 `page.evaluate(async () => { const { apiClient } = await import('/src/api/index.ts'); … })`
造任务：脚本打印「创建成功 `T20260101-0001:pending`」，随后切到调度中心，
**候选池显示「待派任务（0）」、页面一片空**。第一反应是「Mock 的实现漏了一条写路径」。

**根因**：`page.evaluate` 里的动态 `import` 与页面自身加载的模块**不是同一个模块实例**
（Vite dev 给页面用的是带 query 的 URL，另有自身的模块图）—— 于是写进了**第二个** Mock 内存库，
而界面读的是第一个。两边都「工作正常」，只是不在一张表上。

**为什么排除而不是修**：这不是产品缺陷，是**走查工具的用法错误**，改产品去迁就它只会引入
一个为了测试而存在的旁路。真正的解法是让走查**走真实 UI 路径**（点「新建任务」→ 填表 → 提交），
顺带也就验证了这些界面本身。同一轮还踩到第二条同类坑：Mock 是内存库，
**任何 `page.goto`（整页导航）都会连登录态一起重置**，页面间移动必须点左侧导航。

**影响**：这类坑的代价是**走查结论本身失真** —— 脚本说「成功」、眼睛看到「空白」，
若只信其中一边就会得出相反的错误结论（与 `ISS-028`「用 Chrome 打开 `file://` 产物会误判为打包缺陷」同族）。

**处置**：两条纪律写进走查脚本头部注释（`/tmp/udmshot/m4-mock.mjs`）：
① 页面间移动只用页内导航、不 `goto`；② 造数据走真实 UI，不在 `page.evaluate` 里 `import` 应用模块。
本轮 Mock 走查据此重写后，逐项结论与 Electron 形态一致（应用派发 2 单、日志 5 条、控制台错误 0）。

**出处**：走查脚本（临时文件，不入库）· 本批次 `AGENTS.md` 工作日志

## 3. 如何使用本文件

**评审前**：只看 §0.1 的 5 行，就能决定「现在能不能开工、要先定什么」。

**开发中**：开工某模块前，按「领域」列筛一遍相关条目；
开工后若发现新问题，先加进 §1 再动手修（与 `AGENTS.md` 的提交纪律一致：先记录、后提交）。

**提交前**（对应 `AGENTS.md` 提交纪律第 4 步）：

1. 本次修掉的条目 → 状态改「已解决」，并在本文件 §2 追加一行（日期/问题/根因/解法/出处）。
2. 本次新发现的条目 → 按 §1 格式新增，编号顺延。
3. `AGENTS.md` 的工作日志条目里**引用相关 `ISS-xxx` 编号**，两边即可互相追溯。

**与 `AGENTS.md` 的分工再强调一次**：`AGENTS.md` 记「**什么时候发生了什么**」（时间线）；
本文件记「**现在还剩什么问题**」（状态表）。两边都保留，互不替代。
