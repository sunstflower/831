## 1. 本轮要解决什么

使用者给出的目标流程（原话）：

> 「调度中心创建一个新订单 → 调度中心调度一个车来派发这个订单 → 新订单提交告警中心提出可能出现的冲突问题」，
> 前端方面「订单应用后，车可以在前端地图中跑出来（实时仿真地行动就行）」，并「额外设计一个车辆中心」，
> 同时「精简调度中心的内容」。

拆成六项，本文件逐项给出方案：

| --- | --- | --- | --- |
| 1 | 精简调度中心 | `renderer/src/pages/DispatchPage.tsx` · `renderer/src/dispatch/` | 无新编号（页面信息架构调整，见 §5.4） |

## 3. 口径裁决（本文件的核心）

### 3.1 冲突：「订单应用后车就动」 vs 现行「apply 只到 `reserved`、开跑要 `execution:start`」

**冲突事实**：`docs/api.md` §3.4.2/§3.7.3 与 `docs/module-M4-dispatch.md` §10.2 规定 —— 应用派发只把车辆置为 `reserved`，任务进入 `assigned`；让它开跑是另一个权限点 `execution:start` 的动作（D-11）。而使用者本轮要求「订单应用后，车可以在前端地图中跑出来」。

**裁决（新增 D-58）**：保留现行契约与权限分离，**在渲染层把两个动作组合成一个带开关的流程**：

1. 调度中心的应用动作仍是 `POST /api/dispatch/apply`（`dispatch:apply`），服务端行为**完全不变**；
2. apply 成功后，若「派发后立即开跑」开关处于开启状态，且当前会话拥有 `execution:start`，渲染层**逐单顺序**调用 `POST /api/execution/tasks/{id}/start`；
3. 每单的执行结果**单独**汇总（成功 N 台 / 失败 M 台），失败不掩盖已成功的部分，而是逐条给出原因与「去任务管理重试」的入口；
4. 开关默认值 = 当前会话是否有 `execution:start`（有则默认开，没有则整块隐藏并如实说明原因）。

**代价（如实记录）**：`apply` 与 `start` 不再是一个原子动作 —— 存在「已派发但没开跑」的中间态（网络中断、无权限、执行器拒绝）。这是**刻意接受**的：服务端自动开跑会把两个权限点合并，直接推翻 D-11 与既有契约；而「派给谁」与「现在开跑」在真实现场往往不是同一个人。渲染层的顺序调用把这个中间态**显式暴露**给使用者（逐单结果列表），比隐藏它更安全。

**不选的两条路**（写下来免得后来者重走）：

- ❌ 让 `dispatch/apply` 服务端自动 `startTask`：会绕过 `execution:start` 权限（D-11 / D-08），并且 apply 的事务里塞入执行器副作用后，「apply 失败」与「start 失败」两个语义会混成一个错误码。
- ❌ 保持纯手动、只加一句提示：不满足使用者「应用后车就跑起来」的诉求，地图上仍然看不见任何动静。

### 3.2 车辆中心的定位（新增 D-59）

**裁决**：`/fleet` 是**运行态视图**（读模型），不是第二套车辆 CRUD 表单。

- 数据源：`GET /api/monitor/vehicles`（在车辆列表项上补 `currentTaskId`）+ `GET /api/map/overview`（同一时刻的位置/电量）+ `GET /api/map/tracks/{vehicleId}`（轨迹回放）。
- 权限点：**不新增权限点**，页面准入用现成的 `monitor:read`；`base:write` 才显示「编辑 / 启停」入口，并且**跳转到基础数据页**去改，不在本页复制一套车辆表单。
- 理由：车辆表单的唯一作者是 `renderer/src/base/` + `pages/BaseDataPage.tsx`（M2 已落地）。在本页再写一份 vehicle 表单就会得到两处各自演化的校验与字段清单 —— 这正是本项目反复踩过的 D-34（同一事实多个作者）。把「加车」保留在基础数据、把「看车」独立成一页，是本轮成本最低且不产生第二作者的切法。

### 3.3 告警预检的联动方式（不新增接口 / 事件）

`GET /api/alerts/risks`（`alert:read`，`Req-M4-10`）在后端是**从当前车辆—任务—路线派发实时推导**的只读扫描（`shared/src/plan-risk.ts` 纯函数 + `desktop/src/domain/alert/risk.service.ts` 取数），因此：

- 新建订单（`submit: true` → `pending`）后，预检里马上会多出一条「未分配车辆」；
- 派发生效后，预检里的该条会消失，换成对应的占用/时长/电量/迟到判断。

**裁决**：不新增领域事件、不新增接口。调度中心在**创建成功**与**派发成功**两个时点各拉一次 `/api/alerts/risks`，把与该批次相关的条目就地展示；告警中心的两个预检区块（`renderer/src/ops/RiskPanels.tsx`）继续在进入页面时读取全量。两个页面对同一次扫描结果的呈现不同（一个是本批次结论，一个是全量清单），但**判定逻辑只有一份**。

> 若将来要求「告警中心免手动刷新」，正确做法是给 `RISK` 加一个结构类事件并登记 `EVENT_PERMISSIONS`（D-32），而不是让页面轮询 —— 本轮不做，见 §6。

## 4. 端到端流程（实现后应逐字可走通）

```
[调度中心] 新建订单（弹层，复用 M3 表单）
   └─ POST /api/tasks { …, submit: true }        → 任务直接进 pending
   └─ [预检] GET /api/alerts/risks               → 该订单先显示为「未分配车辆」
[调度中心] 待派候选池 → 勾选该订单 → 选策略 → 预览派发
   └─ POST /api/dispatch/preview                 → 对比 / 派发明细 / 拒绝原因
[调度中心] 应用派发（开关「派发后立即开跑」默认开）
   └─ POST /api/dispatch/apply                   → 任务 assigned、车辆 reserved
   └─ POST /api/execution/tasks/{id}/start（逐单）→ 任务 running、车辆 busy、执行器开始推进
   └─ [预检] GET /api/alerts/risks               → 本批次结论（冲突 / 超时 / 电量…）
[地图] 结构类事件 → 重拉快照（路线出现）；位置类事件 → 定向补帧（车辆跑动）
[告警中心] 进入页面 → 全量预检（含该订单派生出的冲突与缺口）
```

### 5.4 精简调度中心的判定标准

「精简」= **首屏只留主链路**，不是删功能：

- 仍常驻：新建订单入口、待派候选池、策略选择、预览与策略对比、派发明细与拒绝原因、派发后预检结论。
- 移入默认折叠的「高级操作」：手动指派、重算（已派发任务）、调度日志、路径规划（试算）。
- 判定：一个从不展开高级区的调度员，仍能独立完成「建单 → 预览 → 派发 → 看车跑」；折叠区的存在不改变任何接口调用。

## 6. 明确不做（避免范围蔓延）

- **不改服务端契约**：不新增 IPC 路由、不新增领域事件、不新增错误码、不新增权限点、不改 `dispatch/apply` 的副作用（§3.1）。
- **不新增执行器倍速接口**：仿真速度仍由执行器常量决定（`DEFAULT_SPEED_FACTOR`，见 `desktop/src/domain/execution/executor.ts`）；把倍速做成可调需要新的运行时设置与文档回写，本轮不做。
- **不在车辆中心复制车辆 CRUD**（§3.2）。
- **不给告警中心加轮询**：预检仍是「进入页面 + 手动刷新」；如需实时，按 §3.3 的注记走事件方案。
- **不实现订单端点图层**（`ISS-011`）与 CSV 导入管线（`ISS-013`/`ISS-014`）：本轮「新建订单」是**手工建单**，不是导入。

## 9. 风险

- 逐单 `start` 是 N 次串行请求，任务多时耗时线性增长；本轮演示规模可接受，若后续放大需先做批量开跑接口（届时要回写 `docs/api.md`）。
- **Mock 形态下车辆会动**：`renderer/src/api/mock.ts` 在首次 `execution/start` 时挂上 1 s 推进定时器
  （`ensureExecutionTimer`），推进算法与主进程共用 `tickExecution`。因此浏览器形态与 Electron 形态
  在本轮的行为应当一致 —— 验收时两种形态都要走一遍，任何一侧不动都要先查定时器是否被挂上。
- 遗留：`renderer/src/api/mock-ops.ts` 的文件头注释仍写「浏览器 Mock 不挂定时器」，
  与上面的实现相反。本轮顺手更正该注释（记录为 `ISS-089`）—— 这类「注释与实现漂移」不会让任何用例变红，
  只能靠读代码发现。

  1. **折叠区比方案多一处**：除「手动指派 / 重算」「调度日志」外，**路径规划也收进折叠区**
     （方案 §5.4 把它列在「移入折叠」里，实现与之一致；但 `DispatchPage.test.tsx` 的旧断言
     假设它是常驻的，本轮改为「先展开再操作」并把这条口径写进用例注释）。
  2. **「在地图上查看这 N 台车」按钮的作用域缩小**：走查发现新建订单后它仍挂着**上一批**的车辆，
     看起来像新订单已经派了车。修法是在 `onOrderCreated` 里一并清掉上一批回执（ISS-091），
     并补一条回归用例（`DispatchNewOrder.test.tsx` 第 2 条）。
- **走查另发现的一处展示口径问题**：车辆中心抽屉把 `x`/`y` 直接印成 `73.59999999999991`
  （`formatNumber` 唯一作者在 `renderer/src/domain/format.ts`），已改为一律走该函数（ISS-090）；
  另一条是「用例与新页面漂移」——`DispatchPage.test.tsx` 仍在断言一个已被信息架构调整移除的徽标
  （ISS-092），它不会让任何东西报错，只会让用例变红并看起来像功能坏了。
- **本文件不记录数值型验收结论**：`npm test` 的套件/用例数、`db:reset` 的行数等一律见
  [`AGENTS.md`](../AGENTS.md) 的「验证基线」与工作日志（D-34：数值只有一个作者）。
